# Writing

Apply these rules in every UI language.

## Voice and tone
- Define a voice from the audience and the feeling wanted (e.g. trust for banking, excitement for games). Keep a list of common terms and reuse them consistently.
- Vary tone by context and what the person is doing: direct for serious situations, light for achievements.
- Be clear: simple, plain language; remove every unneeded word; read aloud when in doubt.
- Most important information first. Several ideas: split across screens.
- Don't be cute or clever in labels: "Send", not "Let's do it!".
- Use possessives sparingly ("Favorites", not "Your Favorites"); if used, stay consistent in perspective. Never use "we" ("Unable to load content", not "We're having trouble loading this content").
- Describe gestures per input type: "tap" for touch, not "click". Small and distant-viewing screens need extra brevity.

## Capitalization and punctuation
- Pick one style per UI element type and apply it everywhere. Title case reads formal, sentence case casual.
- Title case: button labels, menu items, alert titles that are fragments. Capitalize every word except articles, coordinating conjunctions, short prepositions; always capitalize the last word.
- Sentence case: complete-sentence alert titles and informative text.
- Button, menu, and fragment titles: no ending punctuation. Complete sentences: appropriate ending punctuation.
- Ellipsis character (…) on a menu item or button label when the action needs more input or choices before completing.

## Labels and links
- Start button and link labels with a verb; 1-2 words for alert buttons.
- Links: descriptive text ("Learn more about UX Writing"), never "Click here".
- Multi-step flow: start "Get Started"; advance with one consistent term ("Continue" or "Next"); finish "Done".
- Settings: practical label; if needed, describe what happens when on (the off behavior is implied). Link or button to a setting, don't describe its location.
- Window/screen titles: unique and succinct, describing content and purpose.

## Errors
- Prevent first. Show the message next to the problem.
- State what happened and how to fix it; no blame: "Choose a password with at least 8 characters", not "That password is too short". "Use only letters for your name", not "Don't use numbers or symbols".
- No bare or robotic text ("Invalid name", "Error", "Error 329347 occurred").
- No "oops!" or "uh-oh".
- If words can't fix an error that affects many people, redesign the interaction.
- During long work name the real step ("Summarizing key themes"), not "Processing…".

## Alerts
- Direct, neutral, approachable tone; never oblique, accusatory, or masking severity.
- Title: complete, specific, says what happened, where, and why; at most two lines.
- Informative text only if it adds value; as short as possible, complete sentences.
- Don't explain buttons. If guidance is unavoidable, say "choose" (not "tap" or "click") and use the exact button title without quotes.
- Button titles: verbs related to the alert text ("View All", "Reply", "Ignore"). Use specific action titles ("Delete", "Erase") rather than "OK" unless the alert is purely informational. Never "Yes"/"No". Cancel is always titled "Cancel".
- A single default button on a no-choice alert: "Done", not "Cancel".

## Empty states
- Give a clear next step plus a button or link.
- Welcome and teach, in the app's voice, but keep it useful.
- Never put crucial information there; the state is temporary.

## Fields
- Label every field clearly ("Email").
- Placeholder or hint: an example ("name@example.com") or a description ("Your name"). It disappears on typing, so keep a separate label.
- Required data: make clear before proceeding.
- Permission purpose text: one brief, specific, complete sentence in sentence case, active voice, ending with a period.

## Inclusive language
- No unnecessary gendered terms or pronouns: "Subscribers can post recipes to your shared folder", not "his or her". Prefer nongendered imagery for a generic person.
- Ask gender only if required; offer inclusive options (nonbinary, self-identify, decline to state) and let people give pronouns.
- No jargon, slang, culture-specific content, or stereotypes; plain language also eases localization.
- Write about disability people-first; use the terms people use for themselves.
- Don't assume ability, family structure, or circumstances.
- Address people as "you"; never "the user" or "the player".

## Accessibility text
- Every key and custom control needs a nonvisible label describing function; keep current as UI changes.
- Describe only what a meaningful image itself conveys; skip nearby caption content. Hide purely decorative images.
- Charts and infographics: concise description of what they convey.
- Don't convey information by audio alone: provide captions, subtitles, audio descriptions.
- Label interface elements so voice control can target them.
